# 9주차 실습 · 검색·정렬·페이지네이션 게시판 개선

웹서비스설계 9주차 실습 코드를 직접 테스트해 발견한 문제를 수정한 버전입니다.
검색·정렬 보안, 오프셋/커서 페이지네이션, 비동기 요청 처리, URL 상태 복원을 개선했습니다.

## 실행 방법

```bash
npm install express
node server.js
```

- 접속 주소: http://localhost:3000

- 코드 수정 시 저장 후 node server.js를 다시 실행해야 적용됩니다.

## 파일 구성

- `server.js`: Express 백엔드. 1,000건 더미 게시글을 메모리에 생성하고, 오프셋 페이징 API(`GET /api/posts`)와 커서 페이징 API(`GET /api/posts/cursor`)를 제공합니다.
- `index.html`: 게시판 화면(SPA). 검색(300ms 디바운스), 정렬, 오프셋/커서 모드 전환, AbortController 요청 취소, URL 동기화를 담당하고, 오른쪽에 요청 URL·SQL·응답 JSON 검사기를 보여 줍니다.

## 요구사항별 수정 내용

과제 요구사항 순서대로 정리했습니다. **처리** 칸의 "확인"은 기존 코드로 동작함을 테스트로 확인한 항목이고, "수정 N"은 문제를 발견해 고친 항목입니다. 코드 안에는 `[수정N]` 형식의 주석으로 수정 위치를 표시했습니다. 원본과의 비교, 테스트 입력·기대·실제 결과와 캡처는 실습 보고서에 정리했습니다.

### 1. 검색·정렬 (25점)

| 요구사항 | 처리 | 내용 |
|---|---|---|
| 제목·본문 검색 및 결과 없음 처리 | 확인 | 제목·본문 검색 동작, 결과가 없으면 "검색 조건에 일치하는 글이 없습니다" 표시 |
| 최신순·오래된순·조회순, 조회수 동점은 id DESC | 확인 | 조회수가 같으면 id 큰 순으로 정렬됨 |
| 정렬 키 화이트리스트, 잘못된 값은 latest | **수정 1** (server.js) | `abc`는 원래도 latest로 처리됐지만, 실제 적용된 정렬을 확인할 수 없었음 → 응답 `meta.sort`에 적용된 정렬 키를 표시 |
| `__proto__`, `constructor` 등 상속 속성 차단 | **수정 1** (server.js) | `sort=__proto__`는 500 에러, `constructor`는 정렬이 조용히 무시됨 (`SORT_WHITELIST[key]`가 상속 속성까지 찾아냄) → `Object.hasOwn()`으로 직접 가진 키(latest/oldest/views)만 허용 |

### 2. 페이지네이션 (35점)

| 요구사항 | 처리 | 내용 |
|---|---|---|
| 오프셋 페이지 이동, meta 응답 검증 | 확인 | `page`, `limit`, `totalCount`, `totalPages`, `hasNext`, `hasPrev` 응답 |
| `page=0, -1, abc` 및 `limit=1000` 처리 | 확인 | 잘못된 page는 1, limit은 최대 100으로 제한 |
| 검색·정렬 변경 시 1페이지로 초기화 | 확인 | 검색·조회·정렬 변경 시 `state.page = 1` |
| 커서 API에 제목·본문 검색 추가, `limit + 1`로 hasNext 판단 | **수정 3** (server.js)<br>**수정 4** (index.html) | 커서 API가 검색어를 무시했고, 화면도 커서 모드에서 검색어를 보내지 않았음 → 서버는 커서 조건(`id < cursor`) 뒤에 검색 조건을 추가한 뒤 `limit + 1`개로 hasNext 판단, 화면은 커서 요청에도 `search` 전송 |
| 커서는 ID 내림차순 고정, 정렬 선택 비활성화 또는 기준 명시 | **수정 5** (index.html)<br>**수정 3** (server.js) | 커서 모드인데 정렬 선택이 열려 있어 바꿔도 무시됨 → 커서 모드에서 정렬 선택 비활성화 + "최신순" 표시, 오프셋 복귀 시 원래 정렬 복원. 응답 `meta.sort: "id_desc"`로 기준 명시 |
| 검색어 변경 시 누적 목록·커서 초기화, 마지막까지 누락·중복 확인 | 확인 | 검색어를 바꾸면 처음부터 다시 조회. `search=Redis`를 50건 + 33건으로 끝까지 조회해 오프셋 검색 결과(83건)와 일치, 경계(403 → 391)에서 중복 없음 |
| `hasNext=false`이면 더 보기 비활성화 | 확인 | 마지막 페이지에서 버튼 비활성화, 문구 "더 이상 글이 없습니다" |

### 3. 비동기 처리 (30점)

| 요구사항 | 처리 | 내용 |
|---|---|---|
| 300ms 디바운스: 연속 타이핑 후 요청 1회 | 확인 + **수정 6** (index.html) | 타이핑만 하면 요청 1회로 동작. 단, 타이핑 직후 [조회] 버튼을 누르면 남아 있던 디바운스 예약 때문에 요청이 2번 나감 → `applySearch()`에서 `clearTimeout(debounceTimer)`로 예약 취소 |
| AbortController로 이전 요청 취소, 오래된 응답의 덮어쓰기 방지 | 확인 | 새 요청 전에 이전 요청을 `abort()` |
| AbortError 안전 처리 | 확인 | AbortError는 안내 로그만 남기고 일반 에러와 구분 |
| 느린 네트워크에서 검색어를 바꿔 취소·최종 결과 검증 | 확인 | 3G 환경에서 이전 요청 8건 취소, 최종 화면은 마지막 검색어 결과 |

| 요구사항 | 처리 | 내용 |
|---|---|---|
| 오프셋 모드의 검색어·정렬·페이지를 URLSearchParams로 동기화 | 확인 | 페이지 이동·검색·정렬 시 `history.pushState`로 주소 갱신 |

## 개념 설명

### 1. 오프셋과 커서에 적합한 화면
- **오프셋**(`page=3`): 원하는 페이지 번호로 바로 이동할 수 있어 **번호 버튼이 있는 게시판**에 적합합니다.
- **커서**(`cursor=883`): 마지막으로 본 id 다음부터 이어서 가져오므로 **"더 보기" 버튼이나 무한 스크롤**에 적합합니다. 대신 특정 페이지로 바로 이동할 수는 없습니다.

### 2. 디바운스와 요청 취소의 역할
- **디바운스(300ms)**: 요청을 **보내기 전에** 동작합니다. 입력이 300ms 동안 멈췄을 때 한 번만 요청해서 글자마다 요청이 쏟아지는 것을 막습니다.
- **요청 취소(AbortController)**: 요청을 **보낸 후에** 동작합니다. 새 요청을 보내기 전에 아직 응답이 오지 않은 이전 요청을 취소해서, 늦게 도착한 옛 응답이 새 결과를 덮어쓰는 Race Condition을 막습니다.
- 둘은 서로 대신할 수 없습니다. 디바운스만 있으면 느린 네트워크에서 응답 순서가 뒤바뀔 수 있고, 취소만 있으면 요청 수 자체는 줄지 않습니다.

### 3. limit + 1 원리
다음 페이지가 있는지 알기 위해 전체 개수(`COUNT(*)`)를 세지 않고, 필요한 개수보다 **1개 더** 조회합니다. 10개를 원할 때 11개를 가져와서 11개가 오면 `hasNext = true`로 판단하고 10개만 보여 주며, 10개 이하가 오면 마지막 페이지입니다. 전체를 셀 필요가 없어 큰 데이터에서도 비용이 일정합니다.

### 4. offset과 totalPages 계산식
```
offset     = (page - 1) × limit
totalPages = ceil(totalCount ÷ limit)
```
예: 1,000건을 10개씩 보면 `totalPages = ceil(1000 ÷ 10) = 100`, 3페이지는 `offset = (3 - 1) × 10 = 20`이므로 21번째 글부터 10개를 보여 줍니다. 검색 결과가 83건이면 `totalPages = ceil(83 ÷ 10) = 9`입니다.
